# Native Windows (experimental)

CASM can run directly in Windows with Node.js 24+. Its agents then use the
Windows user profile, files, provider logins and MCP configuration. WSL is not
required. CASM starts its own agent sessions; it does not control the desktop
applications' windows or import their existing conversations.

Install and sign into each provider on Windows first. For Claude Code, use the
native executable and install Git for Windows (Claude's Bash tools require it).
Signing into Claude Desktop alone does not necessarily sign into the standalone
Claude Code executable. CASM discovers executables using PATH and PATHEXT,
including npm command shims. For a provider outside PATH, set its non-secret
executable path before starting CASM, for example in PowerShell:

```powershell
$env:CASM_CLAUDE_PATH = 'C:\tools\claude.exe'
$env:CASM_CODEX_PATH = 'C:\tools\codex.exe'
casm serve --listen 127.0.0.1:7373
```

The normal quick-start token and browser flow applies. Use a separate named
token per device. Keep the listener on loopback and use a private HTTPS proxy
such as Tailscale Serve for a phone. The laptop must remain awake and connected.

Windows file references use drive or UNC paths. File-preview links encode these
paths for the browser; the server still checks project boundaries and resolved
targets (including junctions). Explicit `!` commands in Claude sessions run in
Windows PowerShell. Commands generated by the provider use that provider's own
shell configuration. Windows cancellation stops the process tree.

`casm service` currently supports Linux/macOS only and returns an explanatory
error on Windows. For background use, configure Windows Task Scheduler under the
same signed-in user; do not run it as SYSTEM if credentials depend on that user's
profile or DPAPI. Restrict the CASM state directory with NTFS ACLs. POSIX mode
bits such as `0600` do not enforce Windows access control.

MCP configuration and credentials belong to the provider/Windows account; CASM
does not synchronize them from another computer or WSL. Keep service tokens in
your existing credential store, not in per-agent environment settings.

## Validation and remaining work

Native Windows smoke tests covered the real Codex app-server and Claude Agent
SDK, model replies, local stdio MCP access, and the HTTPS browser client. The
platform, filesystem, server and file-link test suites run on Windows, including
process-tree cancellation, npm shim argument quoting, token checks and junction
escape prevention.

The full upstream suite is not yet portable: some fixtures rely on POSIX
shebang executables, Unix permission bits, privileged symlinks and Unix paths.
OpenCode and pi launch paths use the portable spawn adapter but have not been
validated against real Windows installations. Treat this as an initial Windows
port, not a declaration of complete platform parity.
